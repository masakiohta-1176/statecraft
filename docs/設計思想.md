## 出発点 — 分類は破綻する


### 入口に来る質問の形


チャット型のAIアシスタントを、仕様を知らないユーザーへ開いた場合、想定した形の質問は**来ない**。


来るのはこういう形である。


| 来る形 | 何が起きているか |
|---|---|
| 「あれ止まってない？」 | **主語がない。目的語すらない**。何の話かは、答える側が特定するしかない |
| 「◯◯の設定どこ？」 | **用語を混同している**。正式名称ではない、あるいは別の機能の名前で呼んでいる |
| 「これって普通こうだよね？」 | **前提が大幅に間違っている**。質問に答える前に、前提の方を正す必要がある |
| 「昨日の数字おかしいんだけど」 | **実データを見ないと答えられない**。だがユーザーは「実データを確認してから答えて」とは言わない |
| 「◯◯のデータある？」 | **同じ言葉が、まったく違う経路を指している**（[後述](#っていうデータある-同じ言葉が違う経路を指す)） |


**「◯◯の運用手順について教えてください」のような、丁寧に整った依頼は来ない。**省略され、崩れていて、前提が共有されていない。それが普通の状態であって、例外ではない。


重要なのは最後の行である。**ユーザーは手順を指示しない。**実データの観測が必要な質問でも、観測してから答えろとは言わない。何をどの順で調べるべきかを決めるのは、常にシステム側の責任になる。


### 分類の矛盾


こうした質問に対して、まず思いつくのは「分類してから適切な担当へ振り分ける」設計である。質問を受け、カテゴリを判定し、対応する処理へ流す。


**これは原理的に成立しない。**


「この質問は貸出規程の話だ」と正しく判定するには、**貸出規程に何が書いてあるかを知っていなければならない**。書いてある内容を知らずに、そこへ振り分けてよいかは判断できない。


だが、知っているなら分類する必要がない。もう答えられる。


> **分類を正しく行うには、分類した先に隠されている知識をすべて知っている必要がある。**
> **知らないから振り分けたいのに、振り分けるには知っていなければならない。**


分類器に見えているのは、カテゴリの**名前と短い説明**だけである。中身は分類の向こう側に隠されている。**見えていないものへ向けて振り分けようとしている**。これが本質的な矛盾であり、精度の問題ではない。分類器を賢くしても、モデルを大きくしても消えない。


### 誤分類は「それらしい答え」になる


さらに悪いことに、フローは分岐した後に戻れない。


誤って振り分けられた質問は、**エラーにならない**。振り分けられた先の知識だけを使って、そのカテゴリの中で最もそれらしい答えが生成される。他のカテゴリにあった正しい情報は、二度と参照されない。


**間違いが、自信を持って返ってくる。**しかも、どこで曲がったのかは出力からは分からない。


### 結論


**対一般ユーザーのチャット型AIアシスタントを、フローとして組むのは明確に間違いである。**


これは好みの問題ではない。入力が省略され、用語が揺れ、前提が誤っており、必要な手順が語られないという条件下では、事前分類が成立しないというだけのことである。


### ではどうするか


このフレームワークの設計は、すべてここから導かれている。


| 矛盾への対処 | 実装 |
|---|---|
| 分類を1回で決め切らない | 次に何を実行するかを、毎回その時点の記憶（`tasks`）から決め直す |
| 調べてから方向を変えられるようにする | 調べた結果を記憶へ積み、次の判断の材料にする |
| 分類の前に知識へ到達できるようにする | **知識をエージェントの内側へ閉じ込めない**（[後述](#知識をエージェントへ閉じ込めない重要)） |
| 決まっている手順は判断させない | 初期ツールでシステムが先に実行する |


3つ目が、このフレームワークで最も重要な原則である。知識を専門エージェントの中に持たせると、**その知識へ到達するために分類が必要になる**。つまり、上の矛盾を自分から踏みに行くことになる。だから知識は統括側に置き、専門家は「取ってくる手段」として作る。

## マルチエージェントの捉え方


**このフレームワークを読む前に、「マルチエージェント」という言葉から想像するものを一度置いてほしい。**


この語からは、複数の担当者が集まって相談する図を思い浮かべやすい。専門家Aと専門家Bが意見を出し、調整して結論を出す。あるいは、処理を順番に繋いだフローを引く。


**そのどちらでもない。**


### 1つの脳の中の、別々の領域


ここで作っているのは、**1人の脳内にある異なる働きの領域**である。


言語を司る領域と、記憶を司る領域と、判断を司る領域は、互いに「会話」していない。議論もしていない。それぞれが自分の役割を果たし、同じ1つの理解を共有している。分かれているのは役割であって、人格ではない。


このフレームワークの共有記憶は、まさにこの前提の上に立っている。エージェントは互いに報告書を渡し合うのではなく、**全員が同じ1つの記憶を直接読み書きする**。他のエージェントが書いた内容も「自分がすでに知っていること」として読む。


だから、次の3つをしてはいけない。


| してはいけないこと | なぜ |
|---|---|
| **会話をさせる** | エージェント同士のやり取りを設計し始めると、伝達の設計が本題になる。共有記憶を直接読めるのに、わざわざ伝言を作ることになる |
| **議論をさせる** | 複数の見解が生まれると、どちらが正しいかを判定する仕組みが必要になる。それはユーザーが求めた成果と無関係な問題である |
| **フローを繋ぐ** | 処理の順番を固定すると、判断がフローの形に押し込まれる。実際の問い合わせは、次に何をすべきかが事前に決まらない |


3つ目が特に重要である。このフレームワークが**次に何を実行するかを記憶（`tasks`）から毎回決め直している**のは、フローを固定しないためである。順番を決め打ちできるなら、そもそもエージェントは要らない。


### 複数の観点を出すことと、議論させることは違う


2つ目（議論をさせる）は誤解されやすいので補足する。**複数の切り口から分析すること自体は否定していない。**


たとえば「どの方向で進めるべきか」のように、**答えが1つに定まらない**問いでは、観点を分けて分析することに価値がある。売り手側から見た場合、買い手側から見た場合、提供する側から見た場合。切り口ごとに結論が変わるなら、**切り口を並べること自体が成果物**になる。


これはやってよい。やってはいけないのは、**それを議論の形にすること**である。


```
✗  エージェントAとBが互いの意見を読み、反論し、合意点を探る
      → 合意形成の設計が本題になる。負けた側の観点が消える


✓  AとBがそれぞれ独立に自分の観点で分析し、共有記憶へ書く
      → 統括が全部を読んで判断する。観点は消えずに残る
```


**統合するのは統括であって、エージェント同士の合意ではない。**各エージェントは互いに宛てて書くのではなく、同じ記憶へ書く。だから「会話をさせない」と矛盾しない。


そして、**答えが1つに定まる問いで議論させるのは明確に誤りである。**


規程・仕様・手順のように、正解が知識として書かれているものに複数の見解が生まれること自体が異常な状態である。にもかかわらず議論させると、次のどちらかが起きる。


- **もっともらしい方が勝つ**（正しい方ではない）
- **折衷案が生まれる**（どちらでもない第三の答えが出てくる）


後者が特に悪い。**正解が1つ書いてあるのに、書いていない答えが返る。**読めば済むものを、議論というプロセスを通したせいで壊している。


| | 答えが1つに定まる | 答えが1つに定まらない |
|---|---|---|
| 例 | 規程、仕様、手順、設定値 | 方向性、優先順位、打ち手 |
| やること | 統括が知識を読んで答える | 観点ごとに独立に分析し、統括が並べて判断する |
| 議論 | **有害**（折衷が生まれる） | **不要**（並べれば済む） |


この分け方は、[検索の設計](#だから用途を2つに分ける)で述べた2分割とまったく同じ軸である。**答えが1つに定まるかどうか**で、取るべき構造が変わる。


### 有向グラフ的な構築を否定はしない


処理を順番に繋ぐ形（チェーン、有向グラフ）が有効な場面はある。入力と出力が決まっていて、分岐が事前に確定している処理では、そちらの方が速く安く確実である。


**ただし、それを全体の設計に適用してはいけない。**


繋いだ処理は「作業の最小単位」として扱う。このフレームワークでは、それは**1つのツール**になる。ツールの内側が複雑な多段処理であっても構わない。外から見れば「呼べば結果が返るもの」であり、判断の対象になる。


やってはいけないのは、**判断そのものをフローとして固定すること**である。


```
✗  質問 → 分類 → 分岐A/B/C → 検索 → 整形 → 回答
      判断の順番を人間が決め打ちしている


✓  質問 → 判断（何を調べるか決める）→ 実行 → 評価 → 判断（十分か決める）→ ...
      次に何をするかを、毎回その時点の記憶から決める
```


前者は、想定した分岐に収まる問い合わせにしか答えられない。後者は、想定していない組み合わせでも進める。


### 役割の分け方


領域を分けるなら、基本の形は3層になる。


```
利用者
  │
  ▼
受付          要求からノイズを除去して構造化する
  │
  ▼
オーケストレーター   何を調べるか決め、知識を読み、判断する
  │        │
  │ tool   │ 委譲
  ▼        ▼
知識取得    スペシャリスト
検索・参照   専門性・創造性を要する作業
```


#### 受付は判断しない


受付が担うのは2つだけである。


1. **ユーザーの要求からノイズを除去して、構造化する**
2. **戻ってきた記憶を見て、回答に足りる情報が揃っているかを見る**


それ以外は全部後続が持つ。何を調べるか、その順序、可否の判断、どのスペシャリストを使うか——どれも受付の仕事ではない。要求と明らかにズレたものが返ってきた場合に差し戻してもよいが、それは「ズレの検出」であって、正しい手順を指示することではない。


受付に判断させたくなる理由は分かる。入口で分類してしまえば、後続が楽になるように見える。だが[分類の矛盾](#分類の矛盾)で述べたとおり、**入口の時点では分類の材料が揃っていない**。ナレッジを読んで初めて何の話か分かる質問が大半で、受付にはまだ何も見えていない。


だから受付が構造化するのは、**中身の解釈ではなく依頼の形**である。「何を求めているのか」「そのために何が分かっている必要があるか」「何をもって完了とみなすか」を項目として埋める。埋めた内容が正しいかどうかは、読んだ側が判断する。


#### 受付にツールを持たせる基準


**質問の解釈に必要なら持たせる。それ以外は持たせない。**


必要になる典型は、**要求そのものが受付にしか見えない形で届く場合**である。


> 「エクセルに質問入れました」
> （添付ファイルだけが送られてくる）


この時点で、要求は文章として存在していない。表の中や画像の中にある。受付がそれを読んで初めて「何を求められているのか」が言葉になる。だから受付は、添付を開いて中身を取り出すツールを持つ。


添付を後続へ渡さないのは、**あえてそうしている**。利用者からの入力（原文・会話履歴・添付）を受け取るのは入口だけで、委譲で渡るのは構造化された依頼だけである。


理由は**解釈を1箇所に固定するため**である。同じ表や画像を全エージェントが見られる状態にすると、それぞれが自分の解釈を作り始める。どの列が何を意味するのか、どのセルが質問なのか、画像のどこを見るべきなのか——**同じ材料から違う理解が生まれ、そのどれが正しいかを誰も決められない**。そして同じ添付が毎回の生成で入力に乗り続ける。


受付が読んで言葉にした時点で、解釈は1つに定まる。後続はその言葉を受け取るので、解釈し直す余地がない。これは[知識をエージェントへ閉じ込めない](#知識をエージェントへ閉じ込めない重要)で述べた「エージェント間で言うことが食い違う」問題と同じ構造で、**材料を分散させないことで調停そのものを不要にしている**。


一方、在庫を調べるツールは持たせない。それは調査であって解釈ではなく、結果の評価まで受付が抱えることになる。境界は「**それが無いと依頼を組み立てられないか**」で引く。


#### 回答の文章は受付が作る


スペシャリストやオーケストレーターに、利用者向けの文章を作らせない。彼らが返すのは**状態**である（完了したか、何が足りないか）。文章を組み立てるのは、要求を最初に受け取った受付だけが持つ責任になる。


理由は2つある。1つは、途中の層が文章を作ると、受付がそれを引き写すか作り直すかの判断を毎回することになる。もう1つは、文章の中に本来出すべきでない情報（内部のID、テーブル名、審査基準）が混ざる経路が増える。


#### 記憶を持たせるかどうか


受付は記憶を持っても持たなくてもよい。持たない実装（`ReflexAgent`）でも、構造化して委譲し、戻ってきた結果を見て回答する、という流れは成立する。持たせると、複数回の委譲をまたいで「何が揃ったか」を追える。どちらも正解で、要求の複雑さで選ぶ。


### まとめ


- 複数の**人格**ではなく、1つの理解を共有する複数の**領域**
- 伝達ではなく、共有記憶への直接の読み書き
- 固定されたフローではなく、記憶に基づく毎回の判断
- 繋いだ処理は、判断の対象となる1つのツールとして扱う
- 受付は構造化に徹し、判断は後続が持つ


この前提が入っていないと、以降の設計判断はすべて過剰に見える。

## 知識をエージェントへ閉じ込めない（重要）


**知識の取得と情報収集は、統括が担う。専門家に知識を持たせてはいけない。**


エージェントを分けていくと、つい「この領域のことはこの専門家に聞けばいい」という設計にしたくなる。これは避ける。


### なぜ避けるのか


#### 1. 知識へ到達するために分類が必要になる


これが根本的な理由である。[出発点](#出発点--分類は破綻する)で述べたとおり、**正しく分類するには分類の先にある知識を知っている必要がある**という矛盾がある。


知識を専門エージェントの内側へ置くと、その知識に触れるには「どの専門家に聞くか」を先に決めなければならない。決めるための材料は、まさにその専門家が抱えている知識の中にある。**知識を閉じ込めた時点で、この矛盾を自分から踏みに行くことになる。**


統括が知識を直接読めるなら、振り分けは要らない。読んでから決められる。


#### 2. エージェント間で言うことが食い違う


知識を各エージェントへ分散させると、**エージェントAとBが違うことを言った時にどうするか**という問題が発生する。


- どちらが正しいのかを判定する仕組みが必要になる
- 判定するには両者の根拠を比較する必要があり、根拠は各エージェントの内側にある
- 結果として、エージェント間の調停ロジックを作り込むことになる


これは**本質ではない問題**である。ユーザーが求めているのは回答であって、内部のエージェントの意見調整ではない。にもかかわらず、一度この構造を作ると、そこを詰め続けなければ品質が上がらなくなる。


知識を統括に集めれば、この問題はそもそも発生しない。共有記憶に書かれた事実が唯一の根拠であり、比較すべき別の見解が存在しない。


### では専門家は何のために作るのか


**情報を集めるための特別な技能**を持たせるために作る。知識ではなく手段を分ける。


| 専門家に持たせてよいもの | 持たせてはいけないもの |
|---|---|
| 特定の形式のデータを取得する技能 | 「この領域の仕様に詳しい」という属性 |
| 検索クエリを構築する技能 | 仕様やルールそのもの |
| 専門的な判定・設計・構築の作業 | 判断の根拠となる知識 |


たとえば「複雑な条件のクエリを組んでデータを取ってくる」ことは専門家に委ねてよい。しかし「その条件が業務上妥当か」の根拠は統括が持つ。


### 判断の基準


専門家へ委譲してよいのは**作業**であり、**質問**ではない。


```
✗  「この機能の上限値は何件ですか？」        → 質問。統括が自分で調べる
✓  「この条件を満たすクエリを構築してほしい」  → 作業。専門家へ委譲してよい
```


委譲先が返すべきものは「意見」ではなく「成果物」である。成果物であれば、統括はそれを評価して記憶へ書き込める。意見だと、それが正しいかを判定する術がない。


### ドキュメントも統括に置く


参照すべきドキュメント・ナレッジは統括のツールとして持たせる。専門家に持たせると、統括が「専門家に聞かないと分からない」状態になり、判断の主体が曖昧になる。


判断を持ち続ける主体は常に1つにする。

## ナレッジ取得とベクトル検索


知識を統括に置くと決めたなら、次は**どうやって取ってくるか**になる。ここでも[出発点](#出発点--分類は破綻する)で述べた条件がそのまま効く。


### 雑な入力は、そのまま検索の品質になる


ベクトル検索は、クエリの質に強く依存する。


**特徴語を言ってくれれば拾える。**キーワードブーストも効く。ハイブリッド検索も効く。それは正しい。


**だがユーザーは特徴語を言わない。**


さらに悪いのは、**似た概念の単語と混同して質問してくる**という点である。ユーザーの中で2つの概念が混ざっているとき、その混ざった言葉がそのままクエリになる。


> **ユーザー側の混同が、検索側の混同としてそのまま増幅される。**


ベクトル検索は意味の近さで引くので、**混同された概念は「近い」と判定される**。ユーザーが混ぜたものを、検索が丁寧に混ぜ直して返してくる。クエリの雑さを吸収するどころか、雑さに最も弱い形で構造が噛み合ってしまう。


対処は検索側ではなく記憶側にある。似た概念の違いが `back_grounds`（対象のモデル）に言語化されていれば、**ユーザーがAと言いながらBの話をしていることに気付ける**。気付いた取り違えは `hypotheses` へ「混同している可能性がある」として置く。確定していないものを `facts` へ書くと、断定して指摘することになるためである。


**取り違えに気付けるかどうかは、違いが言語化されているかどうかで決まる。**検索の精度ではない。


### 「やり直せ」と言えない、2つの理由


これに対して、「検索結果が意図と違ったらやり直す」「無ければ無いと答える」というループを組みたくなる。**どちらも成立しない。**


**1. やり直しの判定ができない**


意図した結果かどうかを判定するには、**何が正解かを知っている**必要がある。知っているなら検索は要らない。


これは[分類の矛盾](#分類の矛盾)とまったく同じ構造である。判定するために、判定の結果として得たいものを先に持っていなければならない。


**2. 不在の証明ができない**


「そんなナレッジは存在しない」と断言させることは、**全体を見ていない状態で不在を証明させる**ことに等しい。検索で上位N件しか見ていないなら、「無い」ではなく「上位N件には無い」しか言えない。


それでも「無い」と言わせれば、**見ていない場所にあったものを、無いことにして返す**。これは原理的に解決できない。取り直しの回数を増やしても、閾値を調整しても消えない。


### だから用途を2つに分ける


ナレッジ取得におけるRAGは、**性質の異なる2種類**として設計する。同じ仕組みで両方を賄おうとしない。


| | 答えが1つに定まる用途 | 納得度があればよい用途 |
|---|---|---|
| **例** | 規程、仕様、手順、設定値 | 類似案件、事例、参考情報 |
| **検索の役割** | **遠いものだけを除外する** | 近いものを選ぶ |
| **形** | フルコンテキスト検索 | フルベクトル検索 |
| **正しさの基準** | 落としていないこと | 納得できること |


#### 答えが1つに定まる用途 — 選ぶのではなく、捨てる


ベクトル検索を**「選ぶ」ためではなく「捨てる」ために使う**。明らかに関係のないものだけを落とし、残りはすべて渡す。


これで前述の2つの問題が消える。


- 全部見ているので、**不在の証明ができる**（「無い」と言ってよくなる）
- 選んでいないので、**選び間違いが起きない**


クエリが雑でも壊れない。雑なクエリで「明らかに遠いもの」を判定するのは、「最も近い1件」を当てるより桁違いに簡単だからである。**要求している精度が違う。**


#### 納得度があればよい用途 — ただし設計はサボらない


類似案件の提示のように、**利用者が見て納得できれば成立する**用途では、フルベクトル検索でよい。「唯一の正解」が存在しないので、上の矛盾を踏まない。


ただし、**チャンクの切り方と戻り値の設計はサボってはいけない**。ここが雑なままだと、後から検索パラメータでいくら調整しても直らない。


### 性質の違う文章を、検索の工夫で救おうとしない


**まったく性質の違う文章を、検索の重みづけやキーワードブーストで何とかしようとするのは本質ではない。**


規程の条文と、事例の記述と、手順書のステップは、長さも語彙も「1件」の意味も違う。これらを同じ索引に入れて、パラメータで折り合いをつけようとすると、どちらの用途も中途半端になる。**どちらかを良くすると、もう一方が悪くなる**という調整に入り込む。


分けるべきなのは検索パラメータではなく、**索引そのもの**である。用途が違うなら、別のツールとして持つ。


### 「〜っていうデータある？」— 同じ言葉が、違う経路を指す


短く、かつ経路が分かれる例として、次の形がある。


> 「◯◯のデータある？」


**1つの質問に見えて、答えるための経路がまったく違うものが同居している。**


| ユーザーの言う「データ」 | 答えるために必要なこと |
|---|---|
| 実際に記録されている値 | **観測しないと分からない**。クエリを組んで実行して初めて「ある / ない」が確定する |
| 静的に定義されているもの | **定義を引けば分かる**。マスタ、設定、仕様として先に決まっている |


前者は**実行してみるまで誰も答えを持っていない**。後者は**すでに書いてある**。取得手段も、失敗の仕方も、コストも違う。


そしてユーザーは、**どちらを求めているかを言わない**。


言わないのではなく、**言えない**。内部でそれがどう保持されているかを知らないからである。知っていたら聞く必要がない。


ここに「データ関連の質問」というカテゴリを作って分類すると、性質の違う2つが同じ箱に入る。箱に入れた時点で経路の分岐が消えるので、**片方の手段しか持たない担当が、もう片方の質問にそれらしく答える**。定義を引いただけで「あります」と答えたが、実際のレコードは1件も無い、という形で壊れる。


#### これはユーザーの落ち度ではない


強調しておきたい。


> **ユーザーは何ひとつ間違っていない。**
> 同じ言葉が複数の対象を指しうるという構造を、**開発側が整理していないだけ**である。


「もっと具体的に質問してください」と返す設計は、**開発側が整理をサボった結果をユーザーへ転嫁している**。ユーザーは自分が使っている言葉が内部で何段階に分かれているかを知らないし、知る必要もない。


分類が崩壊した原因を入力の質に求めるのは、順序が逆である。**入力は最初からそういうものであり、それを前提に構造を用意するのが開発側の仕事**になる。


#### 何をすればよいか


やることは、賢い分類器を作ることではない。


1. **「データ」が指しうるものを、開発者が先に列挙する** — 観測が要るもの / 定義済みのもの / 両方に跨るもの
2. **取得手段ごとに別のツールとして持つ** — 「観測する」と「定義を引く」を1つのツールに混ぜない
3. **判別できないなら、両方を実行する** — どちらか当てさせるより、両方見てから統括が判断する方が確実で、多くの場合は安い
4. **確定させるべき項目を入力の形にする** — 何を確定できれば答えられるのかを `input_schema` として先に決めておく


4番目が効く。「観測が必要か」を答える側が毎回考えるのではなく、**依頼を作る時点で確定させる項目**にしてしまえば、判断そのものが1回で済み、忘れることもなくなる。


### 一般論を、個別の答えにしない


検索が返してくる知識は、多くの場合「**一般にはこうである**」という記述である。それを今回の対象の答えとして返すと、成立しているか分からない前提の上で断定することになる。


> ある指標が低い、という相談が来る。
> 知識には「その指標の低下は要因Aによる」と書いてある。
> **だが、今回の対象が要因Aの条件に該当するかは分からない。そもそもその構成になっていない可能性すらある。**


にもかかわらず、検索結果としては**これが最も近い記述として返ってくる**。ベクトル検索は意味の近さで引くので、一般論はよく引っかかる。抽象的で語彙が広く、あらゆる個別事例と「近い」からである。


**検索が「関連する記述」を返すことと、それが「今回の答え」であることは違う。**


そして誤りの出方が悪い。一般論をそのまま当てはめても**エラーにはならない**。「原因はAです」という、筋の通った断定が返る。[誤分類が「それらしい答え」になる](#誤分類はそれらしい答えになる)のと同じ形である。


区別は記憶の側で保つ。


| 状態 | 置き場所 |
|---|---|
| 一般論として成り立つこと | `back_grounds`（対象のモデル） |
| 今回の対象がその条件に該当すると**確認できた** | `facts` |
| 一般論を当てはめたが、**まだ確認していない** | `hypotheses` |
| 確認するために観測する / しないと決めた | `decisions` |


**確認していないものを `facts` へ書くと、以降のすべての判断が未確認の前提の上で進む。**しかも後から見ても、それが確認済みだったのか当てはめただけだったのかを区別できない。


#### どこまで調べれば十分か


逆方向の失敗もある。周辺の概念は放っておくと**際限なく広がる**。関連する制度、隣接する仕組み、似た事例。どれも「関係なくはない」ので、止める理由が自然には現れない。


打ち切りの基準は「たくさん調べたか」ではなく、**要求の対象に届いたか**に置く。届いているなら止める。広げるなら、それが要求のどこに効くのかを書けることを条件にする。


そして**その判断自体を `decisions` へ残させる**ことが、膨張を止める仕組みになっている。「なぜ十分と言えるのか」を言語化しなければ止められず、逆に足りないと言うなら何が足りないのかを書かなければならない。**曖昧なまま調べ続けることができなくなる。**


### 本質は、構造理解で雑さを補うこと


対一般ユーザーにおいて本当に必要なのは、検索技術の精度ではない。


> **入力文の雑さを、「質問対象物の構造理解」によって補う構造。**


「あれ止まってない？」に答えられる人間は、検索が上手いのではない。**対象がどういう構造をしているかを知っている**から、省略された主語を復元できる。何が止まりうるのか、今動いているものは何か、この人が普段何を見ているのか。構造を知っているから、欠けた情報を埋められる。


**人間が脳内でやっているのは、検索ではなくこの補完である。**


このフレームワークが構造理解を持つための仕組みは、すでに出てきたものである。


| 構造理解の要素 | 実装 |
|---|---|
| 対象がどういう概念・性質・制約で成り立っているかを言語化して持つ | 記憶の [`back_grounds`](README.md#back_grounds-は対象のモデルを持つ) |
| その知識へ、分類を経由せず直接到達できる | 統括が知識を持つ（閉じ込めない） |
| 何を確定させれば答えられるかを、形として決めておく | `input_schema` |
| 分かったことを積み上げ、次の判断材料にする | 記憶 |
| 決まっている確認手順は、判断させずに実行する | 初期ツール |


検索の精度を上げる方向へ投資する前に、**この構造が入っているかを先に確認した方がよい**。構造が無いまま検索だけ磨いても、雑な入力は雑なクエリのまま通過する。


#### 実際にどう動くか


構造理解が入っていると、こういう依頼に答えられるようになる。


> 「先週借りた本、延長したいんだけど」


**貸出IDも書名も書かれていない。**それでも次のように進む。


| 判断 | 根拠 |
|---|---|
| 求められているのは「延長の実行」である | 参照している情報ではなく、成果物で捉える |
| 延長するには貸出IDが要る | 対象のモデル（`back_grounds`）を知っている |
| IDは、利用者と期間が分かれば特定できる | 同上 |
| 入力に無いが、「先週」と利用者は分かっている | **足りないものを、あるものから埋められる** |
| 特定した結果が1件に定まったので、延長を実行する | 定まらなければ仮説のまま。そこで初めて確認する |


ここで重要なのは、**要求を見失わずに戻ってくる**ことである。


```
✗  「貸出IDを教えてください」        → 特定できるのに聞いている
✗  「先週の貸出はこの3件です」        → IDの特定で終わっている。要求は延長
✓  特定 → 一意に定まったので延長を実行 → 結果を返す
```


2つ目は、**手段（ID特定）が目的（延長）に置き換わる**形である。`goals` を「求められている成果物」で持ち、`tasks` を「何を判断できるようにするための実行か」で書かせているのは、ここで戻ってこられるようにするためである。


そして**これはフローでは書けない**。


```
IDあり / IDなし・利用者と期間あり / 期間が曖昧 / 複数該当 / 該当なし / …
```


事前に分岐を引こうとすると場合の数が増え続け、増やしても想定外は必ず来る。構造を知っていれば分岐は要らず、**「実行に必要なものが揃っているか、揃っていないなら手元の情報から埋まるか」を毎回判定するだけ**で済む。


冒頭で述べた[分類の矛盾](#分類の矛盾)の裏返しである。**分類して振り分けるのではなく、対象を理解して欠けを埋める。**


### 検索の絞り込みは緩くてよい


上記より、初期ツールが知識検索なら**「明らかに関係ないものだけを除外する」程度の緩い絞り込みで足りる**。


コスト面でもこれが許容できる理由が、記憶の仕組みにある。


```
初期ツールの取得結果   … 大きい（数千〜数万文字）
      ↓ 要約
記憶へ書かれる内容     … 小さい（数行）
      ↓
以降のステップで見える内容 … 記憶だけ。取得結果の全文は外れる
```


**初期トークンは比較的大きくなるが、それ以降は圧縮される。** ステップを重ねてもプロンプトが膨らまないため、検索側で極端に削り込む必要がない。


むしろ絞り込みすぎる方が危険で、必要な条件が落ちると「書いていないので答えられない」という結論になり、取り直しのステップが増える。


削りたければ削ってもよい（初期トークンが減る）。ただし**それは最適化であって必須ではない**。優先順位を間違えないこと。
